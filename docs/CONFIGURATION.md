# Configuration — separating operator, CI, and application

The application code does not own the agent's identity. The operator owns
the agent's identity, CI owns the provenance, and the application asks the
library to compose them at startup. Three files, three roles, one runtime.

## The three roles

| Role | Owns | Lives in |
|---|---|---|
| **Operator** | system identifier, owner, scopes, scope→tool map, lifecycle TTL, storage backend | `agent.yaml` |
| **CI / build pipeline** | code hash, policy bundle hash, model hash, build artifact reference | `provenance.json` (CI-generated, never hand-edited) |
| **Runtime environment** | instance ID (hostname / pod name), region, dynamic attestation references | env vars referenced via `env:NAME` in the YAML |
| **Application** | tool function names that match keys in the config | Python code |

If any of those four shifts location — provenance ends up in code, scopes end
up in the application — you are back at the ceremony problem the moment a
field needs to change without a redeploy.

## `agent.yaml` — operator-owned

```yaml
identity:
  adapter: spiffe                   # spiffe | merkle_chain
  data_dir: /var/lib/asid

system:
  identifier: spiffe://corp.example/agents/inbox-triage
  instance_id: env:HOSTNAME         # env:NAME → os.environ[NAME] at startup
  deployment_id: env:ASID_DEPLOYMENT_ID
  environment: prod
  region: env:REGION

owner:
  id: team:platform
  type: team
  responsibility_scope: inbox-automation

attestation:
  chain:
    - local:bootstrap
    - env:ASID_ATTESTATION_REF      # dropped at load time if env var missing

scopes:
  issuer:                           # what THIS envelope may exercise
    - web.read
    - inbox.label
    - text.summarise
  tools:                            # function name → required scope
    web_search: web.read
    apply_label: inbox.label
    summarise: text.summarise
    # Tools NOT mapped here are refused at bind time. Default is deny.

provenance:
  file: ./provenance.json           # CI generates this
  required: true                    # set true in production

lifecycle:
  svid_ttl_hours: 24                # SPIFFE adapter only
```

### Discovery

`IdentityRuntime.from_config()` looks for the YAML in this order:

1. The path passed as an argument: `IdentityRuntime.from_config("/etc/asid/agent.yaml")`.
2. The `ASID_CONFIG` environment variable.
3. `./agent.yaml` (current working directory).
4. `/etc/asid/agent.yaml`.

In production, set `ASID_CONFIG` explicitly in your deployment manifest.

### Env-var interpolation

Any string of the shape `env:NAME` is replaced with `os.environ[NAME]` at
load time. If the env var is unset, the entire field is *dropped* (not set
to empty string). That preserves the operator's intent — "include this
field only when the environment supplies it." Useful for optional
attestation references that may or may not exist in a given deployment.

### Default is deny

The `scopes.tools` block is an allowlist. A function the application tries
to bind that does not appear in `scopes.tools` is refused at startup with
`ConfigError`. Adding a tool requires editing this file, not deploying new
code.

An explicit empty string (`my_tool: ""`) means "bind but do not gate" — for
the rare case where the tool's authorization runs elsewhere and the
identity layer only wants the audit row, not the scope check.

## `provenance.json` — CI-owned

```json
{
  "code_hash": "sha256:a1b2c3d4e5f6...",
  "policy_bundle_hash": "sha256:0011223344...",
  "model_hash": "sha256:aabbccddee...",
  "build_artifact_ref": "ghcr.io/corp/agent:v1.2.3@sha256:..."
}
```

This file is generated by the build pipeline, never by hand. It captures
the four things CI knows that the application does not:

- The exact commit / code hash this image was built from.
- The exact policy bundle bundled into this image.
- The exact model artifact this image will use.
- The exact build artifact reference for traceability.

When the agent reads this file at startup, those hashes flow into the
issued envelope's `provenance` field, which in turn becomes part of the
SVID commitment hash. The audit log row for every action this agent
performs is bound to those four hashes. A verifier holding any audit row
can answer "which build produced the actor that did this?".

### CI integration

A `Makefile` target — same shape as `examples/crewai_identity/Makefile`:

```makefile
CODE_HASH ?= sha256:$(shell git rev-parse HEAD)
POLICY_BUNDLE_HASH ?= sha256:$(shell sha256sum agent.yaml | cut -d' ' -f1)
MODEL_HASH ?= sha256:$(shell sha256sum models/active.bin | cut -d' ' -f1)
BUILD_ARTIFACT_REF ?= $(REGISTRY)/$(IMAGE_NAME):$(VERSION)

provenance:
	@printf '%s\n' \
	  '{' \
	  '  "code_hash": "$(CODE_HASH)",' \
	  '  "policy_bundle_hash": "$(POLICY_BUNDLE_HASH)",' \
	  '  "model_hash": "$(MODEL_HASH)",' \
	  '  "build_artifact_ref": "$(BUILD_ARTIFACT_REF)"' \
	  '}' > provenance.json
```

Run `make provenance` in CI before building the container image so the
file ends up baked into the image at a known path. GitHub Actions / GitLab
CI / Jenkins all support this; the recipe is one shell line.

### `required: true` in production

Set `provenance.required: true` in `agent.yaml` for any non-dev
environment. The agent refuses to start if:

- `provenance.json` does not exist at the expected path, or
- The file exists but `code_hash` or `policy_bundle_hash` is empty.

This converts provenance from "ceremony the developer pasted in once" to
"build-time invariant the agent enforces at startup."

## Application code

The agent's Python looks like this. Note what is and is not present:

```python
from autonomous_identity.config import IdentityRuntime

runtime = IdentityRuntime.from_config()      # picks up agent.yaml + provenance.json

@runtime.identity_tool("web_search")          # scope looked up from config
def web_search(query: str) -> str: ...

@runtime.identity_tool("apply_label")
def apply_label(message_id: str, label: str) -> str: ...

with runtime:
    agent.run(...)                            # every tool call audited
```

**Not present in the application code:**

- The system identifier (`spiffe://...`).
- The owner.
- The build hash, policy hash, model hash.
- The instance ID, deployment ID, region.
- The scope vocabulary (`web.read`, `inbox.label`, ...).
- The mapping from function name to scope.

Each of those is in a file someone else maintains. The application code
does not need to be redeployed when any of them changes. The
`scopes.tools` map is the only contract — function names match config
keys, and the operator controls both sides of that contract.

## Lifecycle operations

Operators can do four things without touching application code:

```bash
# View what an agent currently has authority to do
asid --data-dir /var/lib/asid inspect-envelope --system-id spiffe://corp.example/agents/inbox-triage

# Revoke the agent (next material action fails with LifecycleError)
asid --data-dir /var/lib/asid revoke --system-id spiffe://corp.example/agents/inbox-triage --reason "SOC pulled"

# Verify an audit row from cold storage
asid --data-dir /var/lib/asid verify --audit-ref 'audit://file/...'

# Inspect the full row including the envelope commitment
asid --data-dir /var/lib/asid inspect --audit-ref 'audit://file/...'
```

None of those require restarting the agent. The lifecycle store is the
control plane; the agent's next action checks it before signing.

## Production checklist

Before declaring an agent's identity config production-ready:

1. **`provenance.required: true`** — agent refuses to start without CI-baked provenance.
2. **`identity.adapter: spiffe`** with a real trust domain you control — not the example one.
3. **`identity.data_dir`** points to durable storage (a Postgres-backed lifecycle store via the `[postgres]` extra, or a shared volume).
4. **CI populates `provenance.json` at every build** with real `code_hash` / `policy_bundle_hash` / `model_hash`.
5. **`system.identifier`** matches the workload identity the platform issues (SPIFFE registration entry, k8s service account).
6. **`scopes.issuer`** is the smallest set the agent actually needs.
7. **`scopes.tools`** maps only the tools the agent currently uses.
8. **Tracing** is wired (`TracedIdentity` with `LangfuseTracer` or your OTel collector).
9. **An on-call runbook** documents how to revoke the agent and what the runbook for "agent is acting strangely" looks like.

If any item fails, the path is not the identity primitives — the path is
fixing the config or the build pipeline that produces it.

## When to deviate from this layout

Two cases.

**SPIRE Workload API integration** (planned, not yet shipped). When the
`spire` adapter lands, `system.identifier` will be discovered from the
SPIRE Agent socket at startup rather than declared in `agent.yaml`. The
operator still owns the SPIRE registration entry; the YAML just stops
duplicating it.

**Federated multi-agent flows.** Once you have a second agent, see
[`MULTI_AGENT_INTEGRATION.md`](MULTI_AGENT_INTEGRATION.md) for how to
encode delegation edges in config too. The Stage 2 doc extends this
schema rather than replacing it.
