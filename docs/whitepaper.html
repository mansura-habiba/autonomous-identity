Autonomous Identity An Envelope, Not a Gate.

Agentic systems break the model that identity is a moment of authentication at a single boundary. This whitepaper makes the case for identity as a substrate that travels with the work — and lays out the primitives needed to build it.

1.Executive summary For leadership

An autonomous agent that calls another autonomous agent that calls a tool is three identities deep before it reaches anything that can be locked down. Treating that chain as a sequence of independent authentications is the category error this whitepaper is written to correct.

Identity is not a check at the door. It is an envelope that travels with the work.

The autonomous-identity model frames every agent-mediated action as a signed envelope that accompanies the work as it crosses agents, tenants, tools, and trust boundaries. Each boundary inspects the envelope, attenuates it, signs the transition, and forwards it. The result is a single, replayable record of authority from human user to leaf action — auditable in hours, not weeks.

Three operating capabilities follow from the model:

  • Provenance. Any leaf action — a tool call, a write, a skill load — can be traced back through every hop to the human or system that originated it. No log-diving required.
  • Attenuation. A child envelope can carry strictly fewer capabilities than its parent. Authority can divide. It can never multiply.
  • Federation. Cross-tenant invocation becomes an inspectable handoff with explicit, policy-checked recognition — not an extension of an internal session.

The remaining sections explain how the envelope is constructed, how it attenuates and federates, where it is enforced (gateway, in-process, and at the tool surface), how the audit chain is built, and what this defends against. Section 10 compares the model to OIDC, SPIFFE, and AAuth — and shows where each solves a different problem.

2.Why identity-as-gate fails for agents For leadership

The mistake most architectures make at this point is subtle but consequential. They treat identity the way authentication systems have always treated it: a moment, at a boundary, that produces a session. The session then carries the user's authority forward, undifferentiated, for the duration of the work.

That worked when the work was a human at a terminal. It does not work when the work is a chain of autonomous agents.

Three failure patterns appear the moment a session-based gate meets an agent chain.

The first is session inflation. The user grants broad consent at login. The first agent receives that authority and passes it, undifferentiated, to the next. By the time the tool call fires, the system is acting with the user's full standing on a sub-task the user did not specifically approve. Nothing on the wire records the narrowing the architect intended — because the narrowing was never material.

The second is cross-tenant ambiguity. When agent A in tenant A calls agent B in tenant B, whose identity is on the wire? The user's? Tenant A's service account? Both? A trust decision is being made somewhere, but it usually lives in a request header someone added because the demo failed without it. Federation by side-effect is the operating model. Audit becomes a forensic exercise.

The third is opacity at the tool surface. The agent's capability set expands at runtime — a SKILL.md is loaded, a retrieval result becomes a tool spec, a plugin is fetched from a registry. The gateway sees a call go out. It does not see what the agent decided to run on the way there.

All three failure modes share an address that is not a team or a person. They share an architecture. The architecture says identity ends at the boundary — and the substrate to say otherwise was missing from every catalogue when the work began. The remediation is not new teams. It is the missing primitive.

The architecture fails not because the choices were wrong, but because the question was wrong. The new question is: what travels with the work?

3.The shift: identity as substrate For leadership

In aviation, the Flight Data Recorder does not switch on when an alarm sounds. By the time an alarm sounds, the relevant data has already been produced. The FDR runs continuously. Every control input, every sensor reading, every crew utterance is captured against a synchronised clock so that — months later — investigators can ask which input produced which response and get an answer that is not in dispute.

Identity for agentic systems needs to operate the same way. Not a moment. A continuous, signed record of authority, produced by the system as it works, against a synchronised clock and a known set of issuing keys.

Identity is not a moment. It is a material. Identity is not a check. It is a substrate the system carries.

Three operating properties follow from treating identity as substrate rather than as event:

  • It travels with the work. An envelope is sent on every hop, not minted once and forgotten. Every recipient sees what authorised the call at the moment the call was made.
  • It attenuates as it crosses boundaries. Each delegation produces a child envelope whose capabilities are a strict subset of the parent's. Authority can only narrow.
  • It is signed against a chain. Every transition is countersigned against the previous transition's commitment. The chain is inspectable and replayable end to end.

The substrate is not a new layer in the stack. It is the deliberate carrier of three operating concerns that today get split across half a dozen subsystems: authentication, authorisation, delegation, audit, and the recognition of foreign identities. Naming the substrate forces those concerns to compose, instead of drifting apart.

4.The envelope: what it carries Technical

An access token tells the resource what the caller is permitted to do. An envelope tells the resource what already happened on the way to the call.

A token grants. An envelope attests.

An envelope is a structured, signed record with eight properties. Validation in strict mode enforces all eight. No envelope reaches a policy decision until every property is present and cryptographically vouched for.

The closest cross-industry parallel is the anaesthesia record. An anaesthetist does not hand a patient to recovery on a verbal report. The record carries: who was given what, by whom, when, at what dose, with what response, signed at handover. The receiving team inspects the record before they accept the patient — not the anaesthetist's word for it, the record itself. A handover without the record is a protocol violation, not a courtesy lapse.

The envelope serves the same purpose. The receiving agent does not accept the call on the caller's word. It accepts the call because the envelope — inspectable, signed, traceable to its issuer — vouches for what came before.

Transport

Envelopes travel in a single header, Signature-Key, carrying a JWT-SVID. The choice of JWT-SVID matters: it is the SPIFFE-blessed format for short-lived workload credentials, it is cryptographically pinned to a stable signing key, and it is already understood by the gateways and proxies most enterprises operate. The envelope rides existing rails. It does not require a new transport. 

POST /process HTTP/1.1
Host: worker.tenant-a.demo
Signature-Key: eyJhbGciOiJFZERTQSIsImtpZCI6…
Content-Type: application/json

{ "task": "summarise", ... }

Two things are not in that header that you might expect. There is no bearer token: the JWT-SVID is the credential, and it is not interchangeable with the agent's permanent identity. There is no separate X-User-Id or X-Tenant field: those are claims inside the SVID, and only the SVID's signature vouches for them. Anything else is a hint, not evidence.

5.Delegation and attenuation Technical

OAuth sub-tokens can in principle carry less authority than their parent. In practice — and the empirical record on this is unambiguous — they often carry more, because the issuing service rewrites scopes silently when the client asks for something the parent did not have. The protocol allows it. Operators do it because the alternative is a support ticket.

The envelope model forbids it by construction.

Authority does not multiply. It can only divide.

Three structural properties hold by construction.

Scopes can only narrow. A delegation request is validated against the effective scopes of the parent envelope; any scope not in that set causes the issuer to refuse, with the deny reason scope_not_in_effective. This is enforced before the new SVID is signed. There is no envelope on the wire that ever carried expanded authority.

Depth is bounded. Each child increments delegation_depth. Operators set a maximum (default eight) past which further delegation is refused, full stop. The bound exists because runaway recursive delegation has no good failure mode: it produces audit trees with thousands of leaves and no diagnostic value. Stopping at a known depth keeps the audit chain comprehensible.

Lineage is cryptographic. Each child carries the parent's audit reference and is signed against it. A reviewer presented with a leaf envelope can walk the chain back to the root issuance without consulting any external database. The chain is self-evidencing.

The cross-industry mechanism is the two-key principle from nuclear command-and-control. Two keys must be turned to launch. The operator at the second key cannot turn it without the first key's holder having turned theirs. There is no protocol path that lets the second operator turn both. The envelope works the same way: the child holds a key, but it is the parent's prior signature that unlocks what the child's key can do.

6.Trust domains and federation Technical

Multi-tenant deployments tend to handle cross-tenant calls by accident. An API key. A reverse-proxy header. A service account whose membership drifts from the team that uses it. Federation by side-effect produces configurations no one team owns and no auditor can reconstruct.

A trust domain in this model is the unit of recognition. Inside one trust domain, envelopes verify against a common set of issuing keys and a common policy. Across trust domains, recognition is a deliberate, policy-checked event with an audit record of its own.

Federation is not "we trust them." It is "we trust them to do exactly this, until this time, with these caveats."

A FederationPolicy in the receiving domain declares, in one place, what it accepts: which issuers, what scope prefixes, what jurisdiction constraints, what TTL ceiling, what caveats must be present. Anything else is refused with a named reason. The four named failure modes — trust_domain_not_trusted, jurisdiction_denied, ttl_exceeded, subject_revoked — produce gateway-level responses that an operator can grep for.

The pattern echoes diplomatic mutual recognition. Two jurisdictions agree, in writing, on which documents they will accept from each other, for which purposes, until when. A passport stamped by jurisdiction A is honoured by jurisdiction B because the treaty says it is — not because jurisdiction B trusts whoever is at the desk that day. The treaty is the policy. The stamp is the envelope. The desk is the gateway.

7.Material actions: in-process enforcement Technical

The gateway sees calls. It does not see what happens between calls.

When an agent loads a SKILL.md from a catalogue, that SKILL.md becomes part of the agent's behaviour. When an agent retrieves a tool spec from a registry, that spec defines a capability the agent now has. When an agent evaluates a planner's response, that response shapes what the agent does next. None of those events cross a network boundary the gateway can inspect. All of them change what the agent is about to do.

The gateway is a turnstile. The material action is the airlock.

A material action is a programmatic guard inside the agent process that runs before any state-changing operation. It receives the current envelope, the operation's identifier, and a required scope. It refuses the operation if the scope is not in the envelope's effective set. The refusal emits an audit record with the same chain identifier as the containing call, so the in-process denial appears in the same audit chain as the network-level events that surrounded it. 

identity.run_material_action(
    envelope=current_envelope(),
    action_type="skill.load",
    required_scope=f"claude-skill:{skill_name}",
    fn=lambda: execute_skill_md(skill_md_content),
)

In Demo 4 of the reference implementation, the gateway has already let an A2A skill invocation through and allowed an MCP tool call that fetched SKILL.md content. The envelope satisfied both gateway-level checks. The fetched SKILL.md content lands inside the agent. The material_action guard runs. If the envelope's scopes do not include claude-skill:cloud-finops, the SKILL.md instructions never execute. The fetch was legal. The interpretation was not. The gateway had no way to make that distinction. The material action did.

The cross-industry mechanism is the cockpit voice recorder. A flight data recorder captures sensor and control inputs — the network events of the flight. A cockpit voice recorder captures what happens between radio calls — the conversations, the alarms, the silences. A modern accident investigation needs both. One without the other leaves a blind spot exactly where the human decisions happened.

8.The audit chain: replayable provenance Technical

Logs are diary entries. They record what someone chose to write down. If the writer was wrong, careless, or compromised, the diary is wrong with them. An audit chain has a different ontology: it is evidence the system produced as it worked, signed against the last evidence it produced, unforgeable from inside.

The cross-industry mechanism is chain of custody. A forensic sample is admissible because every handoff is signed and dated by the person taking custody, the tape over the seal is tamper-evident, and the chain of signatures, end to end, is what convinces a court that the sample in evidence is the same one collected at the scene. Breaking the chain at any point — a missing signature, a broken seal — invalidates the sample regardless of how good the science is.

The audit chain operates by the same logic. Each record is signed against the commitment of the previous one. A modification anywhere in the chain changes the commitment, which breaks the chain at every record after it. Tampering is not undetected; it is the chain's loudest failure mode.

If the agent can forge its own evidence, you have a diary, not a ledger.

What replay produces

Replay is the operating capability the chain exists to provide. Given a leaf event — a tool call, a write, a refusal — replay walks backward through the chain to the originating envelope and presents: the human user (or system principal) whose action seeded the chain; every delegation that took place between that root and the leaf; every federation crossing; every in-process material guard that ran; and the exact scope set that authorised the leaf event.

Replay is not log-correlation. There are no joins across services. The chain is one structure; walking it is one operation. The post-incident review that today takes a week takes an hour.

9.Threat model: what this defends against Technical

Envelopes do not make agents safe. They make agent behaviour replayable, which is a different claim. The distinction matters because every honest threat model needs to name what it does not solve.

Five threats are addressed directly:

ThreatHow the model defends
Scope expansion in transit. A downstream agent or proxy rewrites the call to request capabilities the originator did not grant. The receiver verifies the envelope's signature against the trust-domain JWKS and refuses the call if the requested action is not in the envelope's effective scopes. The rewrite never goes through.
Stale or revoked authority. An envelope is replayed after the issuing principal's status changed. Every check resolves the envelope against the issuer's current lifecycle state. subject_revoked and ttl_exceeded deny at the gateway and emit audit records.
Cross-tenant identity confusion. Calls cross tenant boundaries without an explicit recognition decision. Federation is a typed event with a named policy. Cross-domain envelopes either pass a FederationPolicy check or are denied. No call crosses a trust boundary by accident.
Dynamic capability loading. The agent loads a SKILL.md, tool spec, or instruction from a catalogue at runtime, and runs it. material_action guards execution against an in-process scope check. The gateway saw the fetch; the in-process check refuses the interpretation.
Audit tampering. A compromised process attempts to falsify or remove records. Records are committed in a hash chain whose tip is verifiable independently of the writer. Modification changes the tip, which fails verification on the next replay.

Three threats are not addressed, and saying so explicitly is part of using the model responsibly:

  • Model behavioural failures. An envelope cannot detect that an agent is being subtly misled by a prompt injection, a poisoned retrieval result, or a hallucinated tool spec. It can only record what the agent then did. Replay tells you the model decided to call delete_all; it does not tell you the agent should have known better. That is a separate problem class.
  • Physical compromise of the issuing key. If the stable signing key for a subject is exfiltrated, the attacker can mint envelopes that pass every check. Key custody is the underlying root of trust. HSM / TPM / TEE-backed keys move the bar; they do not eliminate the threat.
  • Side-channel exfiltration of envelope contents. The envelope is structured data on the wire. An agent that mishandles it inside its process — logs it at a verbose level, copies it to a debug file — leaks subject and scope information. The model does not enforce confidentiality of envelopes against the process that holds them.

The cross-industry mechanism here is defence-in-depth. Each layer of the stack must fail predictably — open or closed — so that the next layer can compose its assumptions against the previous one. The envelope is one layer. It is the layer that makes provenance and attenuation operational. It is not the layer that decides whether the underlying model should be calling the tool in the first place. That decision belongs to the agent's policy boundary, which is upstream of identity and a different conversation.

10.Compared to OIDC, SPIFFE, and AAuth Technical

Three existing identity systems get cited as alternatives to a model like this. Each solves a real problem. None solves the same problem this does.

System Solves Does not solve
OIDC / OAuth 2.0 Human-to-service authentication and session-bound authorisation across a federation of services with one user at a keyboard. Multi-hop agent chains; attenuated delegation; replayable provenance through tool calls and dynamic capability loading.
SPIFFE / SPIRE Workload identity at the deployment plane: which process is which, signed with short-lived credentials issued to running workloads. What the workload is currently authorised to do on this call; attenuation as authority moves between workloads; cross-workload audit chains.
AAuth (agent JWKS) Per-call agent credentials with stable + ephemeral key separation; clean signing model for agent-to-agent calls. The carrier object's content and lineage; in-process material actions; the audit chain that ties calls into one record.
Identity envelope (this work) The carrier: structured, signed evidence of authority that travels with the work, attenuates across hops, federates across trust domains, and emits a replayable audit chain — including in-process material actions invisible to the network. Workload identity itself (uses SPIFFE for that); the OIDC flow that authenticates the originating human; the policy engine that decides whether a given scope is appropriate (uses your existing engine).

The four compose. OIDC authenticates the human. SPIFFE identifies the workloads. AAuth signs the per-call credential. The envelope carries structured evidence of authority through the chain those three make possible. None of them is a substitute for any of the others. They are four pieces of the same operating story.

The cross-industry parallel is again from aviation. The pre-flight checklist (OIDC), the maintenance log (SPIFFE), the radio sign-on protocol (AAuth), and the flight data recorder (envelope) all coexist. A flight that has only one of the four is not a flight that is "mostly safe." It is a flight that is missing an entire category of failure detection.

11.Deployment patterns Technical

Two enforcement surfaces, deployed together, do the real work: the gateway, which intercepts network calls, and the library, which enforces in-process decisions the gateway cannot see.

Gateway-only is a wall around a building with no doors. Library-only is doors everywhere and no wall.

Pattern A — gateway-managed

Every A2A or MCP call traverses an agentgateway instance. The gateway performs JWT-SVID signature verification, sends the envelope to an ExtAuthz service for verification and effective-scope computation, and evaluates CEL expressions against the resulting scope set. The gateway emits structured access logs that include extauthz.subject, extauthz.scopes, and the audit_ref.

This pattern covers everything the gateway can see: the call exists, the envelope is valid, the scope is permitted for this method or this tool name. It does not cover what the agent does between calls.

Pattern B — library-managed

Inside the agent process, the autonomous-identity library exposes run_material_action as a decorator around any operation whose authority is not visible on the wire. SKILL.md loads, retrieved-plugin executions, planner-emitted shell commands, and similar dynamically-loaded behaviours pass through the guard. The guard reads the current envelope, evaluates the required scope, and either runs the function or raises with an audit-logged denial.

Library-managed enforcement covers what gateway-managed enforcement cannot. The two are not redundant. The two compose.

Pattern C — gateway + library together (recommended)

Production deployments run both. The gateway is the network-surface enforcement point; the library is the in-process enforcement point. Both emit into the same audit chain. A failure at either surface produces a denial with a named reason and an audit record. A successful call has records from both. The combination is what makes the audit chain end-to-end: from the OIDC login at the UI to the leaf MCP tool call inside a foreign tenant's agent, with every refusal and every in-process guard visible in one record set.

The model echoes defence-in-depth in containment systems: the primary containment vessel and the secondary containment building are not redundant — each fails differently, each catches what the other cannot. Removing either reduces the design to a single point of failure no operator would accept.

12.Hard questions

Why not just use SPIFFE-SVIDs directly?

SPIFFE answers "which workload is calling?" cleanly. It does not answer "what authority does this call carry on behalf of which human, with which delegated scopes, against which prior audit reference?" The envelope uses SVIDs as its signing format and SPIFFE trust domains as its boundary unit — and adds the carrier object SPIFFE deliberately leaves out of scope.

What is the performance cost?

Verification is Ed25519 plus a JWKS lookup (cached). The ExtAuthz round-trip adds single-digit milliseconds at p50 on commodity hardware. The material-action guard is an in-process function call with no network I/O. The dominant cost is the cryptographic verification, which is comparable to TLS handshake amortisation and is bounded by the number of hops, not the size of the payload.

Does adoption require every agent to upgrade at once?

No. Both the gateway and the library accept a fallback path where the envelope is absent and the call is treated as low-trust — typically restricted to read-only operations against non-sensitive resources. Migration runs surface by surface: protect the federation boundary first, then the MCP tool surface, then in-process material actions. Each surface is independently shippable.

What happens if the audit log is unavailable?

The library supports a configurable failure mode: refuse all operations whose audit record cannot be persisted (strict), or proceed with a degraded record (development). The conservative deployment refuses, treating audit availability as a hard precondition. The choice is operational, not architectural.

Can the envelope itself be forged?

Only by an attacker holding a stable signing key whose public component is published in a trust-domain JWKS. The same threat that defeats every other cryptographic identity system. The mitigations are the standard ones — HSM / TPM / TEE-backed key custody, short JWKS rotation intervals, and revocation lists that propagate within the SVID's TTL window. The envelope inherits the security of the issuing key. It does not weaken it.

How does this interact with existing policy engines?

Policy engines (OPA / Cedar) evaluate decisions; the envelope provides the inputs. The model is composable: the gateway routes envelope claims into the engine's decision context; the engine returns allow / deny with a reason; the envelope's audit record references the engine's decision identifier. Policy stays where you already write it. The envelope changes what the policy gets to see.
